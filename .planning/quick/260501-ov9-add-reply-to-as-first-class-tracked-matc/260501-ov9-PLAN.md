<objective>
Add `replyTo` as a first-class tracked/matchable rule field, mirroring the treatment of `deliveredTo` everywhere it currently appears. Bulk/marketing senders frequently use unstable `From` addresses but stable `Reply-To` headers; without this, rules can't reliably target them.

Purpose: Close pending todo `2026-05-01-add-reply-to-to-rule-tracked-message-fields.md`. Resolve open questions per planning constraints: (1) `replyTo` matching uses the same semantics as `sender` (glob, case-insensitive); (2) new-arrivals only — no historical backfill of the `move_signals` table or the `proposed_rules` table.

Output: `replyTo` flows through schema, matcher, evaluator, conflict-checker, sender-utils, and the rule-editing UI. The proposal-generation pipeline is intentionally OUT OF SCOPE for this quick task because surfacing `Reply-To` in proposed rules requires a DB schema migration on `move_signals` (add `reply_to` column) and on `proposed_rules`, plus changes to the detector — that's a separate, larger piece of work and the todo's "include Reply-To as a candidate matcher in proposals" bullet is deferred to a follow-up. This plan delivers Reply-To as a *manually-authorable, automatically-evaluated* matcher, which is the part that unblocks the user immediately.
</objective>
